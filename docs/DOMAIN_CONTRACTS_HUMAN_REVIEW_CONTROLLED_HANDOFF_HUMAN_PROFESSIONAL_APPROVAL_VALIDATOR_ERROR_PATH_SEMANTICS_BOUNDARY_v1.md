## 1. Purpose

This docs-only boundary translates the Owner-selected seven-stage semantics for
the future Human Review Controlled Handoff human/professional approval
structural validator's exact error paths, ordering, cascade, descriptor-safe
inspection, and result invariants. It closes the error-path decisions that must
precede any validator-result schema or validator implementation.

The already tracked approval candidate schema remains unchanged. This boundary
creates no validator-result schema, package export, validator, caller,
cross-reference or admissibility checkpoint, approval effect, persistence,
API, route, user interface, audit event, handoff, export, delivery, release,
product candidate, or external-use authorization. It processes no raw,
private, source, case, identity, authorship, or real-evidence material.

Structural validity remains separate from reviewer authority, reference
existence, candidate authenticity, packet membership, fingerprint correctness,
admissibility, approval effect, handoff eligibility, export, delivery, and
release. Human/professional review remains the release gate.

## 6. Indexed Items, Cardinality, And Duplicate References

The three reference arrays are inspected in this canonical order:

1. `decision_basis_refs`
2. `prior_approval_refs`
3. `correction_request_refs`

Within one array, supplied positions are inspected by ascending actual numeric
index. Input order is not sorted or normalized; ascending index is the array's
native positional order.

For each supplied position:

- a hole, accessor-backed index, or non-string data value produces
  `invalid_field_type` at the actual indexed path
- a string that does not match its field's exact schema pattern produces
  `invalid_field_value` at the actual indexed path
- only a data-property string that matches the exact pattern participates in
  duplicate detection

The exact local cardinality errors are:

- an empty `decision_basis_refs` array produces `invalid_field_value` at
  `$.decision_support.decision_basis_refs`
- a `prior_approval_refs` array containing more than one supplied position
  produces `invalid_field_value` at
  `$.decision_support.prior_approval_refs`

The exact correction-request cross-field errors are:

- `HUMAN_PROFESSIONAL_GATE_CORRECTION_REQUIRED` with any count other than one
  locally valid correction reference produces
  `invalid_cross_field_combination` at
  `$.decision_support.correction_request_refs`
- `HUMAN_PROFESSIONAL_GATE_APPROVED` or
  `HUMAN_PROFESSIONAL_GATE_REJECTED` with any non-empty locally valid
  correction-reference array produces the same code at the same path

Duplicate detection is local to one array. It never compares references across
different arrays. The first locally valid exact string occurrence establishes
the seen value; every later locally valid exact duplicate produces one
`duplicate_reference` at its own indexed path. Invalid items do not establish
or match a duplicate value.

A local cardinality or cross-field error does not suppress an independently
applicable later duplicate error. The cross-field error is emitted first under
Section 7. No candidate value is included in an error.

## 7. Deterministic Canonical Error Order And Deduplication

After the root plain-object preflight succeeds, validation emits errors in
these exact seven phases:

| Phase | Exact activity |
| --- | --- |
| 1 | root required fields in declaration order; one root unknown-key error; root field types in declaration order; then locally evaluable root scalar values in declaration order |
| 2 | safely readable `reviewer_attribution`: required fields in declaration order; one unknown-key error; field types in declaration order; then locally evaluable values in declaration order |
| 3 | safely readable `decision_support`: required fields in declaration order; one object-or-array unknown-key error; then field and array-container types in declaration order |
| 4 | reference-array item types and values in array declaration order and ascending actual index |
| 5 | local array cardinality in declaration order: `decision_basis_refs`, then `prior_approval_refs` |
| 6 | the correction-request cross-field rule when its exact participants are evaluable |
| 7 | duplicate-reference detection in array declaration order and ascending actual index |

7

An invalid root preflight emits exactly `invalid_field_type` at `$` and stops
before Phase 1. Missing or invalid parent containers suppress only their own
descendant traversal as defined in Section 8.

Errors are not post-sorted lexicographically and are never ordered by input
property insertion order. After emission, only an identical `{ code, path }`
pair is deduplicated. The first canonical occurrence is retained. Different

## 8. Error Cascade And Cross-Field Evaluability

The cascade is parent-gated and fail closed:

- a non-plain, null, array, special-object, or uninspectable root produces only
  `invalid_field_type` at `$`
- a missing `reviewer_attribution` or `decision_support` produces only
  `required_field_missing` at that parent field path; no missing child errors
  are synthesized
- a present parent field whose value is not a safely inspectable plain object
  produces only `invalid_field_type` at that parent path; no child traversal
  occurs
- a missing nested array field produces only `required_field_missing` at its
  declared path; no indexed errors are synthesized
- an invalid array container produces only `invalid_field_type` at its declared
  array path; no indexed, cardinality, cross-field, or duplicate traversal of
  that array occurs

The correction-request cross-field rule runs only when `decision`,
`decision_support`, and `correction_request_refs` are present and safely
readable, `decision` has a valid declared enum value, the correction-reference
container is an array, and every supplied correction item has valid type and
lexical value. Unrelated errors in `reviewer_attribution`,
`decision_basis_refs`, or `prior_approval_refs` do not fabricate or suppress an
otherwise evaluable correction-request result.

A duplicate among otherwise locally valid correction references does not block
the cross-field phase. The cross-field error, when applicable, precedes later
duplicate errors. No secondary or hypothetical error is derived from a field
whose prerequisite value cannot be safely evaluated.

## 9. Descriptor-Safe Presence And Inspection

A plain-object container has prototype exactly `Object.prototype` or `null`.
Arrays are valid only at the three declared reference-array fields. All own
property descriptors are inspected regardless of enumerability. Inherited
properties are never traversed and never satisfy a required field.

For a known field:

- an own data descriptor establishes presence, including when its value is
  `undefined` or the descriptor is non-enumerable
- `undefined` is present but fails the expected type; it is not missing
- an own accessor descriptor is present but invalid and produces
  `invalid_field_type` at the known field path
- no getter or setter is invoked

For an unknown own key:

- unknown string keys, unknown symbol keys, and unknown accessor-backed keys
  produce one `unexpected_field` at the nearest permitted closed-container path
- enumerability does not change that outcome
- the rejected key name, symbol description, accessor, or value is never read
  into or echoed by the result

For an array, its safe own `length` data descriptor and canonical supplied
numeric index descriptors are recognized. Any other own string or symbol key
fails closed as an unknown key at `$.decision_support`. A non-enumerable numeric
index participates normally. A missing numeric descriptor below `length` is a
hole and receives the indexed type error from Section 6.

Failure of prototype, descriptor, array-length, or own-key inspection produces
`invalid_field_type` at the currently inspected declared container and stops
that branch. Cycles and nested special values cannot create recursive traversal;
they fail at the declared field or index type boundary.
